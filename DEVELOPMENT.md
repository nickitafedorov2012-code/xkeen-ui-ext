## 🧠 Грабли и неочевидные знания (выстрадано отладкой)

Всё ниже — реальные грабли, на которые наступили при разработке. Прежде чем менять
код, работающий с Mihomo/YAML/кодировками — перечитай этот раздел.

### Mihomo REST API (127.0.0.1:9090)

- **`GET /proxies` НЕ содержит прокси из провайдеров!** Только то, что объявлено в
  секции `proxies:` конфига, плюс группы и служебные (DIRECT/REJECT/...). Подписка
  на 100+ серверов через `proxy-providers` в `/proxies` не видна вообще — при этом
  `all`-список группы Fastest их имена содержит. Полный список провайдерных серверов
  живёт в отдельном эндпоинте **`GET /providers/proxies`** (структура:
  `{"providers": {"geodema": {"proxies": [...]}, ...}}`). Панель, показывающая «3
  сервера», — именно поэтому: `get_servers` в `mihomo.rs` читает только `/proxies`,
  надо мержить оба эндпоинта.
- Типы в API — **CamelCase**: `URLTest`, `Fallback`, `Selector`, `Vless`,
  `Shadowsocks` (не `url-test`/`vless`, как в YAML).
- **Reload**: `PUT /configs?force=true` с телом `{"path": "/opt/etc/mihomo/config.yaml"}`.
  Пустой ответ (204) = успех. `"Body invalid"` = сломанный JSON в теле (не в конфиге!).
- Принудительное обновление провайдера: `PUT /providers/proxies/:name` (пустой ответ
  = ок). `exclude-filter` провайдера применяется при его загрузке.
- mihomo запущен без аргументов → конфиг берёт по умолчанию из своей рабочей папки
  (`/opt/etc/mihomo/config.yaml`). Других конфигов нет.
- Версия ядра: 1.19.2x (User-Agent в провайдерах `ClashMeta/1.19.24`).

### Поведение фильтров (проверено на 1.19.2x)

- **Групповой `exclude-filter` НЕ фильтрует провайдеров, подключённых через явный
  `use:`** — только тех, кто подтянут через `include-all: true`. Это ломает «очевидное»
  решение игнора. Рабочий путь: дописывать игнор-подстроки в **собственный
  `exclude-filter` провайдера** (XKeen сам так исключает RU/Hysteria).
- **Пустой `proxies:` в группе = невалидный YAML** → reload отвечает 400, конфиг не
  применяется (при этом старый конфиг продолжает работать — ошибка не фатальна, но
  и не видна). Никогда не вставляй пустой список: `if !kept.is_empty()`.
- Имена провайдерных серверов **дублируют статические**: «Финляндия» существует и в
  секции `proxies:`, и в подписке geodema. Статических серверов в XKeen-конфиге
  обычно 1–2, вся подписка (100+) — через провайдеров.

### YAML-грабли

- **`key:# comment` (без пробела перед `#`) — невалидный YAML**: `#` становится частью
  ключа → `could not find expected ':'`. Вставка маркер-блоков (AUTO-DEVICE) после
  `proxy-groups:`/`rules:` обязана начинаться с `\n`. Ровно это ломал `apply_routing`.
- При построчном переписывании секций групп: проверка «начала новой целевой группы»
  (`- name: Fastest`) должна **сначала сбросить хвост предыдущей** (дописать
  exclude-filter/proxies/include-all), иначе при переходе Fallback→Fastest хвост
  теряется (между группами пустая строка — она не граница секции!).

### XKeen

- XKeen может **перегенерировать `config.yaml`** (в т.ч. при `S05xkeen restart`) —
  наши правки пережили перегенерацию, но watchdog-восстановления ещё нет. После
  рестарта XKeen проверяй, на месте ли правки.
- AUTO-DEVICE-блоки: селектор-группа на устройство (имя кодирует IP:
  `Big PC 192_168_2_118` → `ip_from_group_name` парсит подчёркивания) + правило
  `SRC-IP-CIDR` в `rules:`.

### 🌐 Архитектура перехвата трафика XKeen: почему правила доменов не работают для RU IP без geo_override

- **4 этапа пути пакета от клиента до интернета:**
  1. **DNS на клиенте**: клиент запрашивает IP у роутера (Keenetic `ndnproxy`, порт 53). В XKeen по умолчанию `proxy_dns="off"`, поэтому клиент получает **реальный публичный IP**, а НЕ Fake-IP от Mihomo.
  2. **Сетевой фильтр ядра Linux (`iptables`)**: пакет TCP SYN с клиентского ПК летит на реальный IP назначения. В цепочке `xkeen` стоит фундаментальное правило обхода RU-зоны:
     ```text
     match-set geo_exclude dst ! match-set geo_override dst -j RETURN
     ```
     В ipset `geo_exclude` загружены все IP-диапазоны России (`ru_exclude_ipv4.lst`, ~200 КБ).
     Если IP назначения российский и его нет в `geo_override`, iptables выполняет `RETURN` — пакет уходит **напрямую провайдеру (WAN), минуя Mihomo**! Там его блокирует ТСПУ.
  3. **Вход в Mihomo (`redir-port: 5000`)**: до этого порта пакет **физически не долетает**, если сработал `RETURN` на этапе 2.
  4. **Правила Mihomo (`rules:`)**: правило `DOMAIN-SUFFIX,domain,PROXY` физически не может выполниться, потому что трафик до ядра Mihomo просто не дошёл.
- **Главный вывод:**
  Маршрутизация доменов из веб-панели обязана работать **на двух уровнях одновременно**:
  1. В `config.yaml` Mihomo (правило `DOMAIN-SUFFIX`);
  2. В сетевом фильтре ядра: резолв IP-адресов домена и синхронизация с ipset `geo_override` и файлом `/opt/etc/xkeen/ipset/ru_exclude_override.lst`.
- **Железное правило диагностики:**
  Если сайт не открывается, **никогда не менять конфиг Mihomo вслепую**. Сначала проверить:
  1. `Resolve-DnsName domain` на ПК (какой реальный IP получен);
  2. `ipset test geo_exclude <ip>` на роутере (отсекается ли он ядром в DIRECT);
  3. Счётчик пакетов: `iptables -t nat -L xkeen -n -v` (растёт ли `REDIRECT 5000` или `RETURN`).

### 🖼️ Грабли со статикой, CDN-поддоменами и параллельным DNS (Mysku, Habr и др.)

- **Разные IP у apex-домена и CDN-поддоменов**:
  - `habr.com` (`178.248.237.68`), а картинки и аватарки отдаются с `web.habrastorage.org` (`178.248.233.33`) и `assets.habr.com`.
  - `mysku.club` (`77.246.157.212`), а изображения лежат на `img.mysku-st.ru`, `art.mysku-st.net`, `ext.mysku-st.net` (`77.246.157.105`).
  - У apex-доменов `mysku-st.ru` и `mysku-st.net` вообще нет A-записей (только SOA). Они не резолвятся в IP! A-записи есть исключительно у поддоменов (`img.`, `art.`, `ext.`).
- **Следствие для iptables `xkeen`**:
  Если в `geo_override` добавить только apex (`mysku.club` или `habr.com`), то при загрузке картинок с `img.mysku-st.ru` или `web.habrastorage.org` пакеты направляются на их IP (`77.246.157.105`, `178.248.233.33`).
  Так как это российские IP и их нет в `geo_override`, правило #2 цепочки `xkeen`:
  `match-set geo_exclude dst ! match-set geo_override dst -j RETURN`
  отправляет их в прямой WAN в обход Mihomo (`redir-port 5000`), где они висят и отваливаются по таймауту (`Connection timed out`).
  **Решение**: система обнаружения CDN (`cdn_discovery.rs`) объединяет базу бандлов (`KNOWN_BUNDLES`), параллельный опрос поддоменов (`probe_subdomains`) и быстрый HTML-сканер (`scan_html_cdns`). Все найденные CDN автоматически добавляются в `rules:` Mihomo и их IP синхронизируются в `geo_override`.
- **Последовательный DNS убивает HTTP-запросы**:
  Если для каждого домена опрашивать 15 префиксов поддоменов и резолвить A/AAAA записи последовательно, `POST /api/domains` занимает 20–30 секунд и отваливается по `TimeoutError` на клиенте.
  **Решение**: весь DNS-резолв в `cdn_discovery.rs` и `override_sync.rs` выполняется строго параллельно через `tokio::task::JoinSet` с индивидуальным таймаутом `tokio::time::timeout(1200..1500 ms)` на каждую подзадачу. В результате десятки хостов резолвятся параллельно за ~1 секунду.

### Кодировки: Windows-машина → роутер (главная боль)

- **Кириллица в командной строке plink/PowerShell ломается** (cp866/cp1251
  двойное перекодирование): POST-тело с «Финляндия» превращается в mojibake
  `╨д╨╕╨╜╨╗╤П╨╜╨┤╨╕╤П`, и эта строка сохраняется в конфиг/игнор-лист как есть.
  Правила:
  - POST/JSON с кириллицей — **только через файл**: `curl --data-binary @file`
    (файл писать `[IO.File]::WriteAllText(..., UTF8Encoding($false))`).
  - Файлы на роутер — **только base64** (`base64 -d`), не inline-текст: busybox
    `printf` ломает `\"`, sed через plink ломает кавычки.
  - Даже `[char]0x0424` в PS-команде может исказиться при передаче — проверяй
    байты результата (`[IO.File]::ReadAllBytes` → hex), а не `Get-Content`.
- **Вывод plink → PowerShell-пайплайн декодируется как cp866**: любой UTF-8 дамп
  через пайплайн выглядит как mojibake. Это артефакт отображения, но он же делает
  такие дампы непригодными для суждений о кодировке. Достоверно — только base64
  round-trip или hex байтов.
- Кириллические маркеры поиска в PS-однострочниках (`IndexOf('/// Экранирование...')`)
  искажаются → для правок кода скриптами используй **латинские маркеры**
  (`pub fn ...`, `#[cfg(test)]`).
- Из-за этого в коде появлялись литеральные `$1` и обрезанные строки — после
  скриптовых правок всегда `cargo test` + просмотр места правки.

### Деплой-пайплайн (отработан, порядок обязателен)

1. `cargo test` локально (PATH: `%USERPROFILE%\.cargo\bin;%USERPROFILE%\mingw64\bin`;
   воркспейс на диске `X:` через `subst` — пробелы в пути ломают GNU ld).
2. commit → tag `v*` → push → CI (собирает **только aarch64**) → поллер
   `%TEMP%\xr-poll-ci.ps1` (править имя тега и пути при новом релизе!), ~5–8 мин.
3. Скачать релиз → на роутер через base64+plink (hostkey
   `SHA256:JYD/KYLTxqXSwi7OBY8wkXTO9Cm/8Afrhg88MqfWPIk`, пароль `keenetic`, порт 222).
4. **Порядок: stop → замена бинарника → start** (иначе ETXTBSY).
5. MD5-сверка локального и `/opt/sbin/xkeen-route`.

### Игнор-лист (текущая реализация, v0.2.3)

  `config.json` → `provider_filters` (BTreeMap), восстанавливаются при очистке.
- Открытый вопрос: провайдерная «Финляндия» в тесте не исключилась — либо mojibake
  в сохранённой строке (сломанный POST), либо mihomo применяет `exclude-filter`

  или чисткой кэша провайдера). Чистый ретест: POST через
  `%TEMP%\xr-ig6.json` (байты проверены — корректная UTF-8 «Финляндия»).

### v1.0.14 — поддержка пинга серверов из proxy-providers, исправление приоритетной очереди и полировка UI

- **fix (mihomo-provider-ping)**: в Mihomo эндпоинт `/proxies/{id}/delay` работает только для статических прокси из `config.yaml`, возвращая 404 для всех серверов из `proxy-providers` (подписок). ## Доступ к роутеру (с ПК разработчика)
- plink/pscp лежат в `%TEMP%` (putty-утилиты).
- Подключение: `plink -batch -P 222 -hostkey 'SHA256:JYD/KYLTxqXSwi7OBY8wkXTO9Cm/8Afrhg88MqfWPIk' -l root -pw keenetic 192.168.2.1`
- Копирование: `pscp -scp -P 222 -hostkey '...' файл root@192.168.2.1:/путь` (**только `-scp`** — SFTP на Entware нет).
- **POST-тела через plink не слать** — plink ломает кавычки/кавычки в JSON. Только через файлы (`pscp` + `curl -d @file`) или base64.
- Сложные команды с кавычками/regex: писать в `%TEMP%\xr-cmd.txt` и запускать `plink ... -m %TEMP%\xr-cmd.txt`.
- Вывод plink в PowerShell часто теряется/ломается (cp866). Надёжный паттерн: скрытый bat → `plink ... > %TEMP%\xr-out.txt 2>&1`, затем `Get-Content`. Запуск: `cmd /c start /min "" "%TEMP%\xr-chk.bat"`, потом чтение файла.
- PowerShell показывает UTF-8 JSON как mojibake — это артефакт консоли, данные корректны (проверять hex/curl).

## Сеть роутера: что доступно, что нет
- `raw.githubusercontent.com` — **заблокирован** с роутера.
- Работающие источники: `cdn.jsdelivr.net` и `fastly.jsdelivr.net` (могут кэшировать `@main` с задержкой — см. ниже), `api.github.com`, `github.com` (release-ассеты — напрямую падают по таймауту, нужны зеркала).
- Зеркала для скачивания бинарников: `https://ghproxy.net/URL`, `https://ghfast.top/URL`, фолбэк `http://ghproxy.net/` (у https-зеркал бывают проблемы с сертификатами для curl без CA-бандла; на Entware CA часто нет вообще → в setup.sh везде `curl -k`).
- **jsDelivr кэширует `@main` агрессивно**: purge (`https://purge.jsdelivr.net/gh/...`) не гарантирует обновление на edge, куда попадает роутер. Надёжный путь — релизить тег и ссылаться на `@vX.Y.Z` (теговые URL отдаются свежими). Установщик резолвит ассет через API `releases` (не `latest` — тег latest может быть не проставлен).

## Деплой (пайплайн)
1. Коммит в `main` → тег `vX.Y.Z` → `git push origin vX.Y.Z`.
2. CI (`.github/workflows/build.yml`): собирает фронтенд, кросс-компилирует `aarch64-unknown-linux-musl` через `cross`, публикует prerelease с ассетом `xkeen-route-arm64-v8a`. Сборка занимает 15–40 мин (раннеры бывают медленные/очередь).
3. Обновление роутера: `curl -Ls https://cdn.jsdelivr.net/gh/nickitafedorov2012-code/xkeen-ui-ext@vX.Y.Z/setup.sh | sh` — установщик сам резолвит последний релиз через API, качает бинарник (github → ghproxy → ghfast → http-фолбэк), создаёт init, рестартует. Конфиг сохраняется.
4. Проверка: `sh /opt/etc/init.d/S99xkeen-route status`, `curl -s http://127.0.0.1:1001/api/status`, хэш ассета в `/` должен смениться.

## Грабли из v1.0.2–v1.0.3 (то, что ломало голову — не повторять)

### Диагностика роутера с Windows (plink)
- **Кавычки в `-m`-файле**: файл `xr-cmd.txt` — это ГОТОВЫЙ sh-скрипт, экранировать кавычки для shell НЕ нужно. Паттерн `grep -o '\"name\"…'` (с backslash) в файле ломает кавычки → команда молча даёт пустой вывод. Писать `grep -o '"name[^,]*'` с литеральными кавычками.
- **Кириллица в xr-cmd.txt**: `Set-Content -Encoding ASCII` портит не-ASCII; в командах для роутера — только ASCII, кириллицу/эмодзи из файлов роутера выводить через `base64 -w0` и декодировать на Windows (`[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String(...))`).
- **PowerShell here-string `@'...'@` через терминал портит кириллицу** (теряется первый символ строк, `Финляндия` → `инляндия`). Файлы с кириллицей создавать только через editor tool, не через Set-Content/here-string.
- **Пустой вывод после установки/рестарта панели**: `S99xkeen-route restart` убивает панель — `curl` к `:1001` в этот момент возвращает пустоту. Добавлять `sleep 3–5` перед запросом к API.
- **editor tool**: `new_text` >6000 символов — ошибка; дозапись в конец файла — только через `insert_line` (номер строки узнать заранее: файл может быть не пуст).

### Локальная разработка на Windows
- **`cargo test` И `rustc --test` не линкуются** (windows-gnu: нет mingw, `crt2.o: No such file or directory`; getrandom → dlltool). Это не лечится — не тратить время. Обходная дорога для чистой логики (regex, кодировки, парсинг): **python-модель** алгоритма (python 3.12 установлен) — перенести логику 1:1 и гонять тесты там; в rust — только `cargo check` + тесты в CI.
- **Python-модель должна точно повторять rust-таблицы**: `codecs` cp1251 в python не знает passthrough U+0080–U+009F и рендерит байт 0xB4 как кириллическую `ґ` (U+0491), а не латинскую `´` (U+00B4) — расхождения модели и rust-кода дают ложные падения тестов. Также осторожно с python-ветками вида `elif 0x0490:` — условие-число всегда truthy и молча проглатывает символы.

### Mojibake-ремонт (mihomo.rs)
- **Реальный mojibake бывает cp866-рендерингом**: «╨д╨╕╨╜╨╗╤П╨╜╨┤╨╕╤П» = байты D0 A4 D0 B8… = «Финляндия», «тЪб» = E2 9A A1 = «⚡», «ЁЯЗл» = F0 9F 87 AB = флаг-эмодзи. Без псевдографики в `cp866_byte` (0xB0–0xDF: ╨=U+2568→0xD0 и т.д.) такие строки вообще не чинятся.
- **Смешивание таблиц посимвольно (cp1251.or(cp1252).or(cp866)) порождает новый мусор** («а тЯЗл ЬЯыЗо ⚡⚡⚡»), который проходит `has_cyrillic`. Только строгие таблицы (все не-ASCII символы маппятся в ОДНУ страницу) + выбор лучшего кандидата по score.
- **cp1251 0x80–0xBF НЕлинеен**: Ѕ=0xBD, і=0xB3, ґ=0xB4, є=0xBA, ј=0xBC, ѕ=0xBE, ї=0xBF, Є=0xAA, Ї=0xAF — линейная формула `u-0x0402+0x80` даёт тихо неверные байты.
- **Двойная обработка notes**: если fetch_notes уже срезал маркеры списка, повторный `trim_start_matches(['-','*',' '])` съедает ведущие `**` markdown-жирного. Срезать только префиксы `- `/`* ` (strip_prefix), не посимвольно.

### GitHub / jsDelivr / CI
- **GitHub API (`api.github.com`) с роутера → 403 Forbidden** (rate-limit по IP). Источник версии для самообновления — **jsDelivr API**: `https://data.jsdelivr.com/v1/packages/gh/OWNER/REPO/resolved` → `{"version":"1.0.3"}` (работает с роутера, видит теги сразу). GitHub API — запасной путь.
- **`github.com/.../releases/download/...` с роутера доступен** (302 → объектное хранилище) — скачивание бинаря для самообновления работает. `raw.githubusercontent.com` — заблокирован.
- **`/releases/latest` игнорирует prerelease и draft** — если CI создаёт релиз с `prerelease: true`, кнопка обновления его не увидит. Либо снимать галку в UI GitHub, либо полагаться на jsDelivr (он видит теги).
- **jsDelivr кэширует теги агрессивно** — передвижение тега (`git tag -f`) НЕ обновляет уже закэшированный контент `@vX.Y.Z`. Не полагаться на `@tag` для часто меняющихся файлов.
- **Передвижение тега запускает новый CI-ран**; runner может висеть в `queued` 10–20+ минут — не паниковать и не плодить дубли тегов, просто ждать (проверка статуса: `Invoke-RestMethod https://api.github.com/repos/.../actions/runs?per_page=1` — с локальной машины API работает).
- **Ассет релиза**: `xkeen-route-arm64-v8a` (matrix.name из build.yml), бинарь на роутере `/opt/sbin/xkeen-route`, init `/opt/etc/init.d/S99xkeen-route`.
