## ЧАСТЬ 1. МОДУЛЬ ZAPRET И ЕГО ИНТЕГРАЦИИ

### 🔴 Z-1. Две несовместимые системы блокировок — взаимное исключение Rust↔shell сломано
`backend/src/api.rs:5723-5760` (shell `acquire_zapret_lock`) vs `backend/src/zapret.rs:76-131` (Rust `ZapretLockGuard`).

Shell использует **flock на файл** `/opt/var/run/xkeen-zapret.lock` (если flock есть — на Entware есть), Rust всегда использует **mkdir-lockdir** `xkeen-zapret.lock.d`. Механизмы не пересекаются: панель и S51zapret могут одновременно держать «свои» блокировки и параллельно выполнять конфликтующие операции (рестарт во время старта, watchdog `start-fw` во время `stop`).

Хуже: `release_zapret_lock` (api.rs:5759) в flock-режиме всё равно делает `rm -rf "$LOCKDIR"` — удаляет lockdir, который законно держит Rust-процесс, после чего третий участник считает блокировку свободной.

Сценарий: пользователь жмёт «Перезапустить» в UI (Rust держит lockdir) → Keenetic ndm-хук или watchdog вызывает S51zapret (flock проходит мгновенно) → параллельный stop/start, рассинхрон pidfile и iptables.

### 🔴 Z-2. «Фантомный» апгрейд Zapret 2: бинарник не заменяется, отчёт об успехе есть
`api.rs:7837`: `mv -f "$NEW_BIN" /opt/zapret2/nfqws2` при распаковке из `/tmp/z2_stage.XXXXXX` (другая ФС → mv = copy+unlink).

Если nfqws2 запущен (апгрейд не останавливает службу), `cp` получает ETXTBSY и молча проваливается. Далее: `version.txt` перезаписывается новой версией (7867, 7890), `is_nfqws2_available()` = true (старый файл на месте) → API отвечает `success: true, version: <новая>`, сервис рестартуется со старым бинарником. Версия в UI и на диске врёт.

### 🔴 Z-3. Отключённый Zapret «воскресает» после перезагрузки роутера
Маркер `/opt/var/run/xkeen-zapret.disabled` объявлен в `zapret.rs:17` и `api.rs:5721`, но нигде не проверяется и не создаётся — мёртвый код.

S51zapret лежит в `/opt/etc/init.d/` → Entware стартует его на загрузке безусловно. Пользователь выключил Zapret → ребут → nfqws запущен → watchdog при `enabled=false` просто `continue` (`watchdog.rs:480`) → убивает процесс только `GET /api/zapret/status` (`api.rs:7421-7447`), т.е. когда откроют вкладку. До этого выключенная служба перехватывает трафик.

### 🟠 Z-4. Инъекция в `validate_zapret_conf`: EXCLUDED_IPS/MACS не проверяются
`api.rs:7178-7202`: валидируются только NFQWS_ARGS (чёрный список спецсимволов) и ZAPRET_ENGINE. Значения EXCLUDED_IPS/EXCLUDED_MACS проходят как угодно.

Путь: ConfigEditor → save_config → файл → S51zapret → `api.rs:6027` `for ex_ip in $EXCLUDED_IPS` → `iptables ... -s "$ex_ip"` — значение `$(cmd)` внутри двойных кавычек выполнится как command substitution. RCE из веб-UI (пост-авторизация).

### 🟠 Z-5. GET-эндпоинт с побочным эффектом убийства процессов
`api.rs:7421-7447`: `GET /api/zapret/status` (поллинг каждые 10 сек) делает `kill -9` nfqws и `stop-fw`. Гонка со стартом частично закрыта порядком «сначала конфиг, потом процесс» (~8515), но в самом GET `pidof` читается до чтения конфига, защита держится только на `config_lock.try_lock()`. Любой новый путь запуска, пишущий `enabled=true` после старта процесса, будет убит поллингом. Анти-паттерн: мутации в GET.

## ЧАСТЬ 2. FAILOVER (глубокий разбор, failover.rs 2546 строк)

### 🔴 F-1. Fuzzy-матчинг трафика маскирует падение сервера
`failover.rs:679-696` (`check_active_download_traffic`): `sl.contains(&active_lower)` — трафик сервера «DE-10» засчитывается активному «DE-1». Критерий здоровья «есть живой трафик» (строка 1044) получает чужие байты → упавший сервер считается живым → **failover не переключает**. При этом детектор чёрной дыры и `close_server_connections` используют строгий match — три разные семантики в одном модуле.

### 🔴 F-2. Полный сброс всех соединений роутера
`mihomo.rs:996-1003`: если `close_server_connections(prev)` вернул 0 — включая случай **сбоя GET /connections** (ошибка → тоже 0, mihomo.rs:144-146) — выполняется `close_all_connections()`: рвутся ВСЕ соединения, включая DIRECT (банки, Госуслуги, SIP) и пер-девайсные туннели на других серверах. Прямо противоречит собственному комментарию «DIRECT остаются абсолютно нетронутыми». Затрагивает и speedtest: `run_speedtest` вызывает non-graceful switch_server.

### 🟠 F-3. Ручное переключение ломает настроенную цепочку приоритетов
`api.rs:838-852`: любой ручной выбор сервера переставляет его в `priority_chain[0]` и перезаписывает `priority_server`. Временный выбор «проверить узел» навсегда переписывает порядок отказоустойчивости, заданный пользователем.

### 🟠 F-4. Гонка фонового цикла и ручного прогона
`run_check` не сериализован мьютексом: кнопка «Проверить сейчас» (Dashboard/Settings → `POST /api/failover/check`, api.rs:1203) может выполняться параллельно с фоновым тиком — оба проходят cooldown-проверку, оба пингуют, оба переключают → двойной switch.

### 🟠 F-5. `is_wan_online` — один URL через mihomo
`failover.rs:594-604`: падение ya.ru, DPI-блок или падение самого mihomo = «WAN Down» → failover заморожен при живом канале. Точка отказа там, где проверяют отказ.

### 🟠 F-6. Best-ping режим обходит всю защиту
`failover.rs:883-993`: в этом режиме нет карантина падающего сервера, нет canary, нет детектора чёрной дыры — только 30-сек cooldown. Флаппинг почти не ограничен.

### 🟠 F-7. Failover игнорирует «Служба остановлена»
`watchdog::is_service_stopped()` проверяется всеми watchdog-циклами, но не failover: после нажатия «Стоп» (`set_service_stopped(true)`) failover продолжает пинговать и при частично живом mihomo может переключать серверы и рвать соединения.

### 🟡 F-8..F-12 (мелкие)
Первая проверка после старта — только через `interval_secs` (до часа при больших настройках); карантин в памяти не переживает рестарт панели; `.take(20)` берёт первые 20 серверов в произвольном порядке; stale-снапшот cfg на всю длительность проверки; dedup LAST_WHITELIST_SYNC 2с может пропускать нужную синхронизацию.

### ✅ Сильные стороны failover
Карантин с эскалацией (15/30/60 мин, кап 1ч, амнистия 12ч), гистерезис возврата (calc_hysteresis), canary soak-тест с L7-пробами, «приоритет реального трафика» над синтетикой, строгая граница цепочки, graceful-возврат без разрыва сессий, DIAG-01 изоляция от speedtest, WAN-down заморозка (идея верная), иммунитет ручного выбора к раннему карантину.

## ЧАСТЬ 3. МЕЖМОДУЛЬНЫЕ ВЗАИМОДЕЙСТВИЯ

### 🔴 X-1. Два писателя флага «режим БС» с разными критериями
`GET /api/status` (`api.rs:71-73`, каждые 3 сек: «активный в списках БС») vs `sync_whitelist_mode_tunnel` (`api.rs:711-713`: «autodetect ИЛИ провайдер ИЛИ whitelist.enabled»). При рассинхроне флаг `WHITELIST_ACTIVE` флаппирует → канал на графике мечется БС↔VPS — нарушает железное правило «строго два канала».

### 🔴 X-2. Smart-gaming побеждает приостановку от failover
Failover при переходе на [БС]-узел ставит `gaming_suspended=true` и гасит gaming (во избежание конфликтов сокетов) — но SMART-GAMING watchdog (`watchdog.rs:1002+`) при виде игровых соединений включает gaming обратно, **не проверяя gaming_suspended**. Конфликт, который код пытался предотвратить, воспроизводится.

### 🔴 X-3. Восстановление gaming после ребута без монтажа правил
`main.rs:540-549`: ставит `gaming.enabled=true` и сохраняет конфиг, но не вызывает `sync_gaming_full_tunnel`/`apply_routing` — 7-секундный стартовый синк уже прошёл с `enabled=false`. Итог: UI показывает «включено», трафик не туннелируется.

### 🔴 X-4. Telegram-тумблер Zapret не работает
`bot.rs:574-580`: `cb:zapret_start/stop` вызывает S51zapret напрямую — без обновления `cfg.zapret.enabled`, без блокировки: бот выключил → watchdog вернёт через ≤12 сек; бот включил → `GET /api/zapret/status` убьёт при первом открытии вкладки.

### 🟠 X-5. Стартовые задачи-«гонки на таймерах»
Задачи на 4с/6с/7с/8с (main.rs:449-550) не координированы; adguard-задача монтирует gaming-туннель с хардкодом портов 5000/5001 (Z-9), через 3 секунды gaming-задача перемонтирует с реальными — окно с неверными портами.

### 🟠 X-6. ConfigTx покрывает меньшинство записей
Транзакционный каркас (снапшоты, коллизии, двухфазный откат) — отличный, но все zapret-пути, failover-transition и watchdog-мутации пишут config.json напрямую (`config::save`) без этих гарантий. Плюс мёртвая ветка в collision-check (transaction.rs:403 — mtime-условие недостижимо, хеш уже поймал бы).

### 🟠 X-7. rci::set_clean_dns_servers как скрытый побочный эффект
`api.rs:7669`: каждый apply_preset Zapret добавляет Яндекс/Cloudflare DNS в KeeneticOS + save_config роутера — мутация настроек роутера из «косметического» действия без уведомления пользователя.

## ЧАСТЬ 4. AUTH (auth.rs — прочитан целиком)

### 🟠 A-1. Доверие любому приватному Origin
`auth.rs:543-544`: любой RFC1918 IP считается доверенным Origin → CSRF с любого устройства/сервера в LAN против авторизованной сессии. SEC-08 (XHR-заголовок) от браузерных форм спасает, но вектор со скомпрометированного LAN-устройства валиден.

### 🟠 A-2. change_password при выключенном auth — takeover панели
`auth.rs:462`: текущий пароль требуется только если auth уже включен. При `auth.enabled=false` ЛЮБОЙ запрос может установить свой пароль (enabled=true) → владелец теряет доступ (DoS), отключить обратно без пароля атакующего нельзя.

### 🟡 A-3..A-6 (мелкие)
Токен в JSON-ответе login (XSS-экспозиция помимо HttpOnly cookie); fallback CSPRNG повторяет 32-байтный блок (dest > 32 байт); revoke хранит токены 24ч (безопасно, избыточно); rate-limit 5/мин/IP честный (по peer, не XFF) — ок.

### ✅ Сильно
PBKDF2-100k с автомиграцией с legacy SHA256, constant-time сравнения, HMAC-сессии с отзывом и лимитами, CSRF-guard с SEC-02 тестами на prefix-обход, rate-limit с тестами.

## ЧАСТЬ 5. UPDATER (самообновление панели, прочитан целиком)

### 🔴 U-1. SHA-256 верификация факультативна
`updater.rs:579`: хеш ищется в ТЕКСТЕ релиза (extract_hash_from_checksum_text(rel.body)); в человекочитаемых «Что нового» его нет → проверка молча пропускается. SEC-01 не работает: защита от подмены бинарника = ELF-магия + тестовый запуск --version, которые пройдут вредоносному бинарнику. Нужен обязательный checksum-файл в релизе или подпись.

### 🟠 U-2. Нет авто-отката при падении новой версии после рестарта
Рестарт fire-and-forget (722-729); `.bak` существует, но автоматически не возвращается; watchdog на саму панель отсутствует → «кирпич» UI до ручного вмешательства по SSH.

### 🟡 U-3..U-5 (мелкие)
UPDATE_LOCK внутрипроцессный (два экземпляра панели обновятся параллельно); staging-мусор при панике между copy и restart; fetch_latest берёт notes из jsDelivr@tag — если тег свежий, CDN может ещё не иметь (фолбэк на встроенный DEV_MD смягчает).

### ✅ Сильно
Стриминг с хешированием на лету, ELF-архитектурная проверка (включая endianness для MIPS!), тестовый запуск до замены, staged rename в целевом каталоге (без cross-device), регенерация init-скрипта до рестарта.
