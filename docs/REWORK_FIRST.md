## Шаг 0. Бэкенд-тесты не собираются (без этого шлюз не даст GREEN ни одному багу)

### Баг 37: в тесте есть, в коде нет
> Обновление 2026-11-06: функции уже есть, backend-тесты собираются; проверка failsafe принимает только HTTP 204 и дополнена проверкой имени моста. Полный прогон: `=== GATE OK bug 37-rework | diff 6edb899420e5 | лог docs/fix_logs/bug-37-rework-green.log ===`. Описание ниже сохранено как исходные замечания ревизии.
- В `backend/src/zapret.rs` (тест около строки 824) вызываются `is_failsafe_http_status_valid(u16)` и `has_lan_bridge_interface(&str)`. Этих функций нет, поэтому `cargo test` падает с `E0425`.
- Рабочий код `verify_zapret_failsafe` не изменён:
  - ответ засчитывается при любом коде от 200 до 399;
  - проверка LAN проходит по `interfaces.contains("br") || interfaces.contains("Bridge")`.
- Что исправить:
  1. Считать «интернет есть» только при ответе **204**. Оба адреса проверки — `generate_204`. Captive portal отвечает на них 200 с HTML.
  2. Код 3xx в проверке вообще не появится: общий клиент `state.http` (`main.rs`, `reqwest::Client::builder()...build()`) сам идёт по редиректам. Либо проверять строго `== 204`, либо делать отдельный клиент с `reqwest::redirect::Policy::none()`.
  3. Мост искать по имени интерфейса: строки `/proc/net/dev`, левая часть до `:`, имя начинается с `br` (или `Bridge`). Желательно ещё проверить, что он поднят (`/sys/class/net/<имя>/operstate` = `up`).
- Тест нужно поправить, это его усиление, а не ослабление: сейчас он требует, чтобы 200 считался успехом, то есть закрепляет баг.
- Отрицательный пример LAN в тесте проходит и на старом коде, так что RED он не даёт. Нужен пример, где `br` встречается не в имени интерфейса.
- RED должен падать на поведении, а не на компиляции. Сначала добавь функции, повторяющие **старую** логику, получи RED, потом исправляй.

## Шаг 1. Переоткрытые баги (в журнале были FIXED, но исправлены не до конца)

### Баг 1: при падении AdGuard фоновые синхронизации снова шлют DNS сети на мёртвый порт
- Исправлено:
  - когда сторож видит мёртвый AdGuard, он вызывает `remove_adguard_iptables`;
  - тот возвращает XKEEN_BS и XKEEN_GAMING на DNS Mihomo.
- Не исправлено:
  - `resolve_active_dns_port` (api.rs) всегда вызывает `resolve_active_dns_port_with_health(cfg, true)`;
  - вариант с `false` вызывается **только в тестах**.
- Из-за этого все рабочие вызовы считают AdGuard живым:
  - api.rs — около 7 мест;
  - failover.rs:1797;
  - main.rs:513/632/653;
  - watchdog.rs:548/1078/1423;
  - transaction.rs:924.
- Любой failover или DHCP-сторож снова направит DNS сети на порт мёртвого AdGuard.
- Ещё одна проблема: при восстановлении (`adguard.rs`, `build_sync_tunnel_dns_ports_script(..., 1053)`) порт 1053 зашит в код, а не взят из `dns.listen` (связано с багом 45).
- Готово, когда:
  - здоровье AdGuard (например, флаг, который выставляет сторож по `test_agh_dns_listener`) учитывается в `resolve_active_dns_port`;
  - тест показывает, что при мёртвом AdGuard рабочая функция возвращает порт Mihomo.

### Баг 13: найденные сканированием CDN стираются из geo_override
- Исправлено: появилась единая функция `override_sync::sync_from_config(cfg, extra_cdns)`, и прямых вызовов `sync_geo_override(&` вне модуля нет.
- Не исправлено:
  - найденные CDN нигде не хранятся, а 8 мест передают пустой список `&[]` и при каждом вызове стирают их:
    - api.rs:2217, 4354, 12141, 12279 (рядом с этими строками);
    - bot.rs:1450, 1465, 1478;
    - watchdog.rs:236;
    - main.rs:702;
  - это ровно подпункт аудита «тумблер игрового режима стирает найденные CDN».
- Тест `regression_bug_13_geo_override_has_single_source_of_truth` проверяет только отсутствие прямого вызова и этого не ловит.
- Регресс от исправления: `collect_override_domains` не исключает домены, которые Zapret-hybrid ведёт в DIRECT. Раньше `force_add_domain` их отфильтровывал (`is_zapret_direct_domain`). Проверить, не попадают ли IP DIRECT-доменов в geo_override.
- Готово, когда:
  - результат последнего скана сохраняется в конфиг или кэш и всегда входит в `collect_override_domains`;
  - тест показывает, что после скана вызов `sync_from_config(cfg, &[])` не теряет CDN.

### Баг 70: часть вызовов iptables всё ещё без `-w`
- Исправлено: AdGuard, XKEEN_DIRECT, `build_*_commands`, скрипт Zapret (обёртка `iptables()` с `-w 2`).
- Без `-w` остались:
  - очистка при старте и рестарте XKeen в api.rs (около строк 2270–2296, переменная `$ipt` без `-w`, около 20 команд);
  - проверки сторожа Zapret: watchdog.rs:616, 668, 704;
  - чтение статусов: api.rs около 8033, 8130, 8883, 8910, 9745, 10405, 10414, 10423, 10837.
- Чтение без `-w` при занятом xtables lock даёт ложное «правил нет», и сторож зря перезапускает Zapret.
- Готово, когда ни в одном рабочем (не тестовом) shell-фрагменте нет `iptables`/`ip6tables` без `-w`, и это проверяет тест по исходнику.

### Баг 91: DNS-rebinding закрыт только для изменяющих запросов
- `is_legitimate_host` проверяется только внутри CSRF-проверки для POST, PUT, DELETE и PATCH (`auth.rs`, `auth_middleware`).
- Если авторизация выключена, GET-запросы к `/api/*` и `/clash/*` через rebinding (Host: evil.com) по-прежнему отдают данные: настройки, логи, устройства.
- Готово, когда:
  - для всех `/api/` и `/clash/` запрос с нелегитимным Host отклоняется;
  - тест на GET с `Host: evil.com` проходит.

### Баг 36: «любой процесс nfqws считается нашим», подпункт не исправлен
- В `zapret.rs`, около строки 235 (функция проверки PID), `comm == "nfqws"` или `cmdline.contains("nfqws")` даёт `true` для любого процесса nfqws.
- Готово, когда «нашим» считается только процесс с нашими аргументами (`--qnum=200` или наш путь к конфигу и hostlist), и это проверяет тест на примерах cmdline.

### Баг 114: проверка не закончена
