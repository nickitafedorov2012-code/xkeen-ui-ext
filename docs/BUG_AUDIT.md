## Находки проходов 1–5
Перенесено из чата без изменений. Пункт 12 подтверждён в проходе 4 (комментарий BS-PIN в коде).

### Проход 1–3

#### Критичные: интернет или DNS пропадают у всей сети

1. **При падении AdGuard в режиме БС вся сеть теряет DNS.**
   - Сторож при падении AdGuard возвращает DNS на 1053 только в игровой цепочке XKEEN_GAMING ([adguard.rs:1315](backend/src/adguard.rs:1315), [watchdog.rs:850](backend/src/watchdog.rs:850)). XKEEN_BS стоит первой в PREROUTING и продолжает слать DNS всей сети на мёртвый порт.
   - То же происходит при «Остановить AdGuard».
   - Кроме того, `resolve_active_dns_port` ([api.rs:10319](backend/src/api.rs:10319)) не проверяет, жив ли AdGuard. Любая последующая синхронизация (DHCP, failover) снова направляет DNS на мёртвый порт.

2. **Исключение устройства из БС не работает для обычных устройств.**
   - UI отправляет MAC ([Whitelist.tsx:933](frontend/src/components/Whitelist.tsx:933)).
   - `resolve_excluded_whitelist_ips` ([routing.rs:2054](backend/src/routing.rs:2054)) находит IP по MAC только для устройств из игровых или БС-списков. Поиск по `device_routing` никогда не срабатывает: там ключи — IP, а не MAC.
   - В итоге UI показывает «исключено», а устройство по-прежнему идёт через БС.

3. **В режиме БС (StrictXKeen) правила, стоящие выше catch-all блока БС, обходят его.** Это игровые правила, принудительные домены (→PROXY), персональные доменные правила устройств и Zapret-hybrid (YouTube и Discord → DIRECT, AI → PROXY).
   - Если БС включён вручную, PROXY смотрит на VPS, и появляется третий канал трафика, что нарушает правило двух каналов.
   - DIRECT для YouTube при белых списках просто не работает.
   - Всё, что стоит ниже catch-all (правила устройств, расписания, Flow), не срабатывает никогда.

#### Игровые режимы и их конфликт с БС

4. **После перезагрузки игровой режим включается на узле БС.** [main.rs:566](backend/src/main.rs:566) определяет «узел БС» без учёта подписки. Если на 8-й секунде Mihomo ещё не отвечает, результат тоже «не БС». Тогда [main.rs:592](backend/src/main.rs:592) включает игровой режим и снимает флаг `gaming_suspended`, и БС с игровым режимом работают одновременно.
5. **Ручное включение игрового режима при активном БС ничем не блокируется** (`toggle_gaming` / `save_gaming_config`). Умный режим проверяет только `gaming_suspended`, поэтому при вручную включённом БС он тоже включает игровой.
6. **Страница «Игровой режим» сохраняет весь снимок конфига** ([Gaming.tsx:416](frontend/src/components/Gaming.tsx:416), [Gaming.tsx:463](frontend/src/components/Gaming.tsx:463)).
   - Стирает игнор-лист: «Не реагировать» обновляет только `status`, а не `cfg`.
   - Откатывает фоновое включение или выключение умного режима.
   - Снимает приостановку игрового режима, которую поставил failover на время БС.
7. **Умный режим подменяет режим пользователя.** Если выбран KnownServices или SmartSplit, при первом же игровом соединении режим принудительно меняется на Compatibility ([watchdog.rs:1205](backend/src/watchdog.rs:1205)).
8. **Умный режим и тумблер игрового режима рвут соединения всей сети.** Они вызывают `switch_group`, который закрывает все соединения LAN ([watchdog.rs:1240](backend/src/watchdog.rs:1240), [api.rs:10274](backend/src/api.rs:10274)). Это та же проблема, которую раньше исправили в расписаниях.
9. **Умный режим пишет config.yaml без транзакции.** Ошибки reload игнорируются, а config.json сохраняется в любом случае, и конфиг расходится с ядром.
10. **Умный режим следит только за первым устройством** (`find`). Если играет второе устройство, по таймауту простоя игровой режим выключается у всех.
11. **Распознавание игр неточное** ([watchdog.rs:1049](backend/src/watchdog.rs:1049)).
    - Любой UDP на порт ≥1024 считается игрой: торренты, WireGuard, Zoom. С торрентом таймаут простоя не наступает никогда.
    - Включение срабатывает от Discord в фоне или от просмотра магазина Steam.
    - Проверка `rule contains "gaming"` смотрит на тип правила, а не на группу, и никогда не срабатывает.
12. **Выбор «Выходной узел» из подписки для игрового устройства, вероятно, ломает конфиг Mihomo.** В правило подставляется сырое имя ноды из подписки ([routing.rs:1848](backend/src/routing.rs:1848)). Mihomo, по моим данным, такое не принимает (proxy not found). Тумблер откатится с ошибкой. Умный режим запишет такой конфиг без отката, и следующий старт Mihomo упадёт.
13. **Ipset `geo_override` перезаписывают шесть мест, каждое своим набором доменов.** Записи последнего побеждают:
    - сохранение доменов стирает игровые домены и CDN;
    - тумблер игрового режима стирает найденные CDN;
    - при старте синхронизация не идёт вовсе, если нет принудительных доменов.
14. **Игровые правила стоят выше AdBlock, DIRECT и персональных доменных правил.** Персональные правила для игровой консоли поэтому не работают, хотя в коде они описаны как «наивысший приоритет». `custom_domains` в режиме Compatibility применяются ко всем устройствам сети, а не только к игровому.
15. **Discord нужен двум функциям сразу.** Игровой режим ведёт его в 🎮 Gaming и добавляет в `geo_override`, а Zapret hybrid_discord — в DIRECT. Молча побеждает игровой режим.
16. **Три настройки игрового режима ни на что не влияют:**
    - `gaming.zapret` (управление Zapret);
    - `exclude_fake_ip_for_game_domains` (по умолчанию включён и обещает защиту, которой нет);
    - `force_redir_host_for_devices`.
17. **Единственное выключенное игровое устройство считается активным.** Так работает запасное правило `len == 1`, и оно повторено в пяти местах.

#### Google AI (Antigravity и Flow)

18. **Прокси Antigravity недоступен с ПК.** Он слушает на `127.0.0.1` ([antigravity.rs:617](backend/src/antigravity.rs:617)), а UI выдаёт команду `AG_LS_PROXY=http://<IP роутера>:53129`.
19. **Режим (auto/direct/proxy) и «Собственный прокси» сохраняются, но бэкенд их нигде не использует.**
20. **Обход через подменный IP работает только когда клиент спрашивает DNS напрямую у ndnproxy.**
    - При AdGuard, БС или игровом режиме DNS идёт мимо `ip host`.
    - Подменный IP не исключён из XKEEN_BS и XKEEN_GAMING. Mihomo читает SNI, и правило Flow отправляет трафик в прокси. Два механизма Google AI мешают друг другу.
21. **Antigravity не отступает при сбое.**
    - Когда рабочего IP нет (healing/error), мёртвый IP остаётся в `ip host`, и Google AI не работает.
    - Если IP не изменился, правила не применяются заново. После сброса правил роутером они не восстанавливаются.
    - При смене списка целей старые записи не удаляются.
22. **Список подсетей Google неполный** ([antigravity.rs:215](backend/src/antigravity.rs:215)): нет 172.253/16, 192.178/15 и подсетей GCP. Если эталонный DNS не ответил, настоящий IP Google считается «подменным», и трафик идёт напрямую под геоблок.
23. **Приоритет Flow зависит от посторонней настройки** ([routing.rs:3224](backend/src/routing.rs:3224)).
    - Без БС Flow стоит выше всего, включая DIRECT и FORCE пользователя и AdBlock.
    - С БС Standard Flow стоит ниже них, а safeguard Zapret отправляет AI в PROXY вместо выбранного `flow_server`.
    - `google.com` в Flow перекрывает DIRECT для `play.google.com` в профиле Smart TV.

#### DNS

24. **DNS-политика БС (российские домены → DNS роутера) применяется только при явно заданных устройствах** ([routing.rs:2312](backend/src/routing.rs:2312)). В основном режиме Zero-Touch без списка устройств её нет, хотя правила при этом действуют на всю сеть.
25. **Перезапись DNS-порта переставляет правила в XKEEN_GAMING.** При перезаписи порта AdGuard правила переносятся в конец цепочки через `-A`, и TCP-DNS попадает за общий TCP REDIRECT. NDM-хуки 060 и 061 при этом хранят старый порт.

### Проход 4

#### Zapret

26. **Community hostlist дублируется при каждом сохранении** ([api.rs:7478](backend/src/api.rs:7478)). Блок `START COMMUNITY HOSTLIST` не вырезается: он считается «ручными строками» и добавляется заново при любом переключении. Файл растёт на тысячи строк за раз, и после выключения функции старые копии остаются.
27. **Утечка правил iptables.** `add_fw` добавляет в nat PREROUTING правила `-d 127.0.0.1 RETURN` и RETURN для DNS исключённых IP, а `remove_fw_rules` их не удаляет. С каждым restart, reload-fw и срабатыванием NDM-хука цепочка растёт.
28. **Когда Zapret падает, YouTube и Discord перестают работать у всей сети.** Сторож после 5 неудачных запусков ставит `zapret.enabled=false`, а failsafe в скрипте снимает правила. Но правила Mihomo никто не пересобирает. YouTube и Discord остаются в DIRECT уже без DPI-обхода.
29. **`set_features` сохраняет весь снимок из UI.** Он затирает исключения устройств со страницы «Устройства», статистику community-списка и выбранный движок. «Сбросить» вдобавок выключает Zapret и удаляет все исключения устройств.
30. **Сохранение zapret.conf в редакторе не пересобирает правила Mihomo.** Флаги в конфиге и правила маршрутизации расходятся.
31. **DPI-инструмент меняет DNS всей сети.** Если AdGuard выключен, Zapret перенаправляет DNS сети на жёстко заданный порт 1053.
    - Флаг `ADGUARD_ENABLED=1` ставится, если AdGuard просто установлен, даже выключенный.
    - `DNS_REDIRECT_REMOVE_CMD` удаляет все чужие правила с `to-ports 1053` и не восстанавливает свои, когда Mihomo поднимается.
32. **Исключение устройства из Zapret работает только для трафика, который идёт с LAN напрямую.** Hybrid-трафик через Mihomo DIRECT выходит из роутера через OUTPUT с адресом роутера и всё равно проходит DPI. Исключение по MAC переводится в IP через ARP только при старте.
33. **Discord voice ставит в очередь nfqws весь UDP 50000–65535 со всей сети.** Через userspace идут игровые пакеты, и пинг растёт. Это конфликт с игровым режимом.
34. **В очередь всегда идёт только TCP 80/443, а qnum и fwmark зашиты в код.** Пользовательские аргументы с `--filter-udp=443` (QUIC) или другим `--qnum` молча ничего не делают.
35. **Два копипаст-сериализатора zapret.conf.** Тесты проверяют неиспользуемую копию ([zapret.rs:537](backend/src/zapret.rs:537)), в работе другая ([api.rs:7637](backend/src/api.rs:7637)). В обеих путь `/opt/etc/xkeen-route/config.json` зашит в код и игнорирует `--config`.
36. **Ошибки сторожа Zapret.**
    - При выключенном Zapret любое чужое правило на 1053 запускает stop-fw каждые 12 секунд.
    - Любой процесс `nfqws` в системе считается «нашим».
    - Сторож держит `config_lock` на всё время старта скрипта, до ~20 секунд, и все сохранения в это время блокируются.
37. **Проверка failsafe ненадёжна.** Ответ 3xx (captive portal) засчитывается как «интернет есть», а проверка LAN `contains("br")` проходит всегда.

#### Белые списки

38. **Включение одного устройства в БС включает БС на всю сеть** (`toggle_whitelist_device`). В стратегии StrictXKeen это перехват всей LAN. При этом не синхронизируются ни iptables, ни телеметрия. Выключение последнего устройства режим БС не выключает.
39. **Целевой узел БС из подписки ломает конфиг.** В правило catch-all подставляется сырое имя ноды, и Mihomo не принимает конфиг.
40. **Сохранение закреплённых устройств рвёт соединения всей сети столько раз, сколько закреплено устройств** (в цикле вызывается `switch_group`).
41. **В режиме БС IPv6 не перехватывается совсем.** Ip6tables-правил нет, и IPv6-трафик идёт напрямую в обход БС.
42. **Обещанное исключение для подписки не реализовано.** Комментарий в `is_whitelist_server_full` говорит, что в подписке БС можно оставить отдельные обычные серверы, но код считает БС все серверы такой подписки.
43. **`toggle_whitelist_device` ищет устройство и по IP.** Если DHCP выдал IP другому устройству, у старой записи перезаписывается MAC.

#### Хардкод (критичный)

44. **AdGuard открыт в WAN.** `AGH_LAN_INTERFACES` включает `apcli+`, а это WISP-WAN (на вашем роутере WAN — `apcli1`). Поэтому DNS со стороны WAN перехватывается в AdGuard. Правило `INPUT ACCEPT` на порт AdGuard не ограничено интерфейсом, и AdGuard доступен как открытый резолвер из сети провайдера.
45. **DNS-порт Mihomo 1053 зашит примерно в 100 местах.** Он нигде не читается из `dns.listen`: игровой режим, БС, AdGuard, скрипт Zapret, сторож. При другом порту DNS пропадает у всей сети.
46. **Порты 5000/5001 тоже не всегда берутся из конфига.** Где порт не найден в config.yaml, молча подставляется значение по умолчанию, без предупреждения.

#### Переходы и интерфейс

47. **Навигация по `#diagnostics` не работает.** Обработчик back/forward не знает `diagnostics`, `bs` и `whitelists`, хотя при загрузке страницы эти адреса понимаются. Кнопка «назад» на диагностику и ссылки `#bs` игнорируются.
48. **Переключение вкладки молча теряет несохранённое.** Компонент вкладки размонтируется, и пропадают правки в «Настройках», доменах игрового режима, Antigravity, черновиках zapret.conf и hosts, а также в «Белых списках». Нет ни подтверждения, ни `beforeunload`.
49. **Нет анимаций переходов.**
    - Вкладка появляется мгновенно, а на месте загрузки мигает карточка высотой 340 px.
    - Тосты исчезают без анимации.
    - Каждое переключение заново загружает данные, и вёрстка прыгает.
50. **Нет тестов на конфликты кнопок.** Сейчас ни один тест не проверяет комбинации: БС + игровой режим, AdGuard + БС, Zapret + Discord, умный режим + ручной, сохранение со старым снимком.

### Проход 5

#### Google AI (Flow)

51. **[К] Узел из подписки, выбранный для Google AI, ломает каждое сохранение в панели.** Если в конфиге нет группы «Google AI», правила Flow указывают на сырое имя ноды ([routing.rs:3224](backend/src/routing.rs:3224)). Это происходит при каждой пересборке маршрутов, а Mihomo такой конфиг не принимает. Кнопки «Починить» и «Автоподбор» выбирают именно такие ноды из группы PROXY.
52. **«Починить Google Flow» без группы Flow всегда возвращает ошибку.** Проверка ищет группу с «google ai»/«flow» в имени. К этому моменту config.yaml уже изменён, а `flow_server` не сохранён, и при следующей пересборке изменение откатывается.
53. **«Автоподбор сервера Google AI» — только флаг.** Фоновой задачи нет, узел подбирается один раз.
54. **Переключение маршрута Google AI дважды рвёт соединения всей сети.**
55. **Пинг для выбора узла Google AI ненадёжен.**
    - В режиме БС пингуются VPS из PROXY, которые при белых списках недоступны.
    - Страна узла определяется по имени, и « by » в английских названиях считается Беларусью, такие узлы исключаются.

#### Zapret

56. **[К] Каждый запуск Zapret из UI меняет системные DNS роутера.** Start, restart, start-fw и reload-fw вызывают `set_clean_dns_servers`.
    - В конфиг Keenetic добавляются жёстко заданные 77.88.8.8, 77.88.8.1 и 1.1.1.1, затем выполняется `system configuration save` (запись во флеш).
    - Никогда не удаляются, перебивают DoH пользователя.
    - 1.1.1.1 при БС заблокирован.
57. **[К] Вкл/выкл Zapret из бота не пересобирает правила Mihomo.** После выключения YouTube и Discord остаются в DIRECT без DPI. При неудачном старте сохраняется `enabled=true`. У UI для того же действия своя, другая реализация.
58. **Старт и стоп Zapret из UI пишут config.yaml без транзакции.** Ошибка reload игнорируется.

#### Telegram-бот

59. **[К] «Режим паники» не держится.**
    - Failover с автовозвратом за несколько минут возвращает VPS.
    - БС, игровой режим, Google AI, группы устройств и XKEEN_BS не трогаются, так что «100% DIRECT» неправда.
    - Сохраняется имя сервера, а не ID: при алиасах «Возобновить» не срабатывает. После перезапуска панели состояние теряется.
60. **AdBlock из бота повторяет баги, исправленные во втором пакете для API.** Защита включается до коммита, DNS-редирект и туннели не синхронизируются.
61. **Бэкап через бота отправляет секреты в Telegram в открытом виде.** В файле хеш пароля, `session_secret`, токен бота и URL подписок.

#### Failover

62. **[К] В режиме Best-Ping нет возврата с БС на VPS.** Ветка Best-Ping завершается раньше логики автовозврата ([failover.rs:2903–3134](backend/src/failover.rs:2903)). Узел [БС] остаётся активным, пока сам не упадёт, а `auto_restore_priority` игнорируется.
63. **Порог пинга в Best-Ping работает только без трафика.** Любой живой трафик делает медленный узел «здоровым». Гистерезис мешает переключению, даже когда активный узел выше порога, а кандидат ниже.

#### Устройства и белые списки (UI)

64. **[К] Пакетное «Сервер для N устройств» (`/api/routing`) не сохраняется в `device_routing`.**
    - Выбор ноды существует только в runtime и пропадает после рестарта Mihomo.
    - UI этих назначений не видит.
    - На каждое устройство вызывается `switch_group`, то есть N полных сбросов соединений.
65. **Одно устройство может одновременно быть игровым, исключённым из БС, исключённым из Zapret и иметь свой маршрут. Проверок нет.** Пример: игровой Compatibility + БС Strict + исключение из БС. Срабатывает RETURN в XKEEN_BS, игровая цепочка подавлена, и устройство идёт полностью напрямую, хотя UI показывает «игровой режим включён».
66. **Тумблер «Авто-БС при failover» заодно переключает `follow_failover`.** Это две разные настройки, а UI меняет их одной кнопкой.
67. **Закрепление узла отправляет весь массив устройств из UI.** IP, обновлённые DHCP-монитором, затираются.

#### Обновления

68. **Проверка SHA-256 подписана как обязательная, но пропускается.** Если контрольная сумма не опубликована, бинарник ставится без проверки.
69. **Хеш берётся из того же релиза, что и бинарник.** Подписи нет, так что проверка защищает только от битого файла, но не от подмены.

     после рестарта, его никто не восстанавливает — панель недоступна до SSH. updater.rs:680–690, 749–770.
128. **Бот авторизует по `chat.id`, а не `from.id`:** если целевой чат — группа (отрицательный ID разрешён), любой
     участник управляет роутером: переключение, режим паники, обновления, бэкап с секретами (п.61).
     bot.rs:237, 251, 270.
129. `/speedtest` в боте не берёт `speedtest_lock`: идёт параллельно с failover и speedtest из UI; два снимка
     групп откатывают друг друга. bot.rs:923.
130. [К] **Повреждённый config.json → ВСЕ настройки заменяются дефолтами** (сохраняется только auth); первое же
     фоновое сохранение записывает дефолты навсегда. Пустой файл (потеря питания, п.94) не содержит следов auth →
     панель без пароля. config.rs:1266–1300, 1305–1330.
131. Автооткат commit-confirmed восстанавливает снимки YAML и config.json целиком: стирает всё, что за окно
     изменили другие (failover, watchdog, другие вкладки); iptables не пересинхронизируются; ожидание только в
     памяти — рестарт в окне = отката нет. transaction.rs:853–950.
132. Третья копия распознавания тега БС (миграция конфига) — расходится с остальными (не учитывает подписки).
     config.rs:1215–1235.

Проверено и чисто: `xkeen_service` и AdGuard-сервис валидируют путь init-скрипта; повреждённый config.json
бэкапится в `*.corrupted.<ts>.bak`; закрытие соединений при переключении селективное.

## Проход 10 (блоки B7–B8 фронтенд)

133. [К] **«Сохранить настройки интеграции» AdGuard отправляет весь снимок `AdGuardConfig` с момента открытия
     страницы** (включая `enabled` и `dns_port`); бэкенд целиком заменяет `config.adguard` и пересобирает
     маршруты. Если watchdog за это время нашёл другой порт или сам включил AGH, сохранение поля «хост»
     откатывает порт/включение → DNS-редирект на неверный порт (INV-2). AdGuard.tsx:305, api.rs:11610–11640.
134. Быстрая блокировка домена в AdGuard сохраняет весь текст редактора правил: несохранённые правки и
     устаревший список уходят целиком, правила, добавленные в веб-UI AGH после загрузки, стираются; при ошибке
     поле не откатывается. AdGuard.tsx:283–298.
135. [К] **Игровой режим с вкладки «Устройства» создаёт игровое устройство без IP**: UI шлёт только MAC, бэкенд
     пишет `ip: ""`, а правила Mihomo и iptables строятся по IP → режим «включён», трафик не перехватывается.
     IP дозаполняет только DHCP-сторож и только в Compatibility. Devices.tsx:506, api.rs:11272–11292.
136. «В прокси» из монитора соединений: при ЛЮБОЙ ошибке force-add (таймаут, когда бэкенд уже применил; ошибка
     валидации) идёт запасной путь — повторное применение, read-modify-write `domains` (гонка с другими
     вкладками) и правило с жёсткой целью `PROXY` (группы может не быть, INV-4). ConnectionsViewer.tsx:335–366.
137. «Напрямую в 1 клик» берёт «корневой домен» по двум последним меткам: для общих хостингов (github.io,
     cloudfront.net, amazonaws.com, appspot.com, workers.dev, vercel.app, akamaihd.net) и незнакомых
     двухуровневых TLD (com.au, co.kr, com.cn) в DIRECT уходит весь суффикс для всей сети; IP уходит как домен;
     IPv6-хост превращается в «[2a00». ConnectionsViewer.tsx:65–87, 386–405.
138. Переключатель Zapret у устройства не блокируется на время запроса — двойной клик шлёт два противоположных
     запроса. Devices.tsx:460–490.
139. Обновление статуса после тумблера теряется: `xr:refresh-status` пропускается, если опрос уже в полёте, а
     летящий запрос возвращает состояние до изменения → тумблеры «отскакивают» до следующего тика. App.tsx:244–280.
140. Проверка обновлений панели опрашивается дважды (App и Header, каждая раз в минуту); обновление Mihomo
     сравнивается строками (`lat !== cur`) — на более новой/альфа-версии предлагается «обновление» (откат).
     App.tsx:179, Header.tsx:198, 213–220.
141. Токен Telegram-бота отдаётся открытым текстом в `GET /api/settings` (маскируются только пароли/секреты RCI,
     Mihomo, AdGuard); `merge_settings_update` не понимает плейсхолдер `******` — клиент, вернувший
     замаскированный раздел, затрёт секрет литералом. api.rs:580–625, 656–668.
